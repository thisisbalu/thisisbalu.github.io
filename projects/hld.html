✅ Functional Requirements Must Have
  • Shorten URL — given a long URL, return a unique short code (e.g. sho.rt/aB3xY)
  • Redirect — visiting the short URL redirects to the original long URL
  • Custom alias — user can optionally choose their slug
  • Expiry — URLs can have a TTL (default: never)
  • Analytics — click count, geo, device (nice-to-have → deep dive)
⚙️ Non-Functional Requirements Scale & Reliability
  • High availability — redirects must work 99.99%. Writes can tolerate brief unavailability.
  • Low latency — redirect < 10ms p99 (cached), < 50ms uncached
  • No collisions — two long URLs must not share a short code
  • Unpredictability — codes shouldn't be guessable/sequential
  • Durability — once created, a short URL must never silently disappear

🗄️ Deep Dive 2: Database Schema
-- Core table CREATE TABLE url_mappings ( short_code VARCHAR(8) PRIMARY KEY, long_url TEXT NOT NULL, user_id BIGINT, created_at TIMESTAMPTZ DEFAULT NOW(), expires_at TIMESTAMPTZ, click_count BIGINT DEFAULT 0 ); CREATE INDEX idx_user ON url_mappings(user_id); CREATE INDEX idx_expiry ON url_mappings(expires_at) WHERE expires_at IS NOT NULL;
💡 For scale: shard by short_code (consistent hashing). short_code is the read hot path — keep it as primary key.
🚀 Deep Dive 3: Caching Strategy
  • Cache-aside (Lazy loading): App checks Redis first. On miss → DB → write back to Redis
  • TTL on cache entries: Match URL expiry. Prevents stale redirects post-expiration
  • Write-through on creation: Warm the cache on URL creation (avoids cold start on viral URLs)
  • 301 vs 302 redirect: 301 = permanent (browser caches, no server hit next time). 302 = temporary (server always sees request — better for analytics). Choose based on analytics need.
  • CDN at edge: Cache 302 responses at CDN edge (with short max-age) for geo-distribution
⚠️ Interview trap: "301 is better for performance but breaks analytics." State this trade-off clearly — it shows you think beyond the happy path.

🔥 What Separates Good from Great Answers
  • Mention 301 vs 302 trade-off unprompted — shows product depth
  • Call out Thundering Herd: A viral URL causes a cache miss storm. Mitigate with cache stampede protection (mutex on miss)

  • Scale-out: App servers are stateless → horizontal scale trivially. DB sharding by short_code hash is the main scaling challenge to discuss

1
Alice sends message

2
Persist + sequence

3
Route to recipient

4
Chat Server B delivers

Read receipt

Clients deduplicate using msg_id — if the same message arrives twice (retry scenario), it's shown once.
📴 Offline Delivery Flow (Bob is offline)
1
Session Service lookup: Bob has no active connection (last_seen > 30s ago → offline)
2
Message stored in Bob's Offline Inbox (persistent queue per user)
3

⚠️ Push notifications are best-effort — APNs/FCM don't guarantee delivery. The offline inbox is the source of truth. Always drain inbox on reconnect, don't rely on push alone.
🗂️ Message Storage Schema
-- Cassandra: partitioned by conversation, sorted by sequence CREATE TABLE messages ( conv_id UUID, msg_id BIGINT, -- Snowflake ID: timestamp + seq (monotonic per conv) sender_id UUID, content TEXT, media_url TEXT, msg_type TINYINT, -- 0=text, 1=image, 2=video, 3=voice status TINYINT, -- 0=sent, 1=delivered, 2=read created_at TIMESTAMP, PRIMARY KEY ((conv_id), msg_id) ) WITH CLUSTERING ORDER BY (msg_id DESC);
💡 "Cassandra is ideal here — it partitions by conv_id (so all messages in a conversation land on the same node) and sorts by msg_id for efficient range reads."
🔢 Deep Dive 1: Message Ordering Most asked!
  • The problem: Alice sends M1 and M2 rapidly from her phone. Network reorders them. Bob sees M2 before M1. Or Alice's phone + laptop both send — which arrived first?
  • Client-side sequence number: Each client maintains a per-conversation sequence counter. M1=seq:1, M2=seq:2. Server rejects out-of-order.
  • Server-assigned monotonic ID: Chat server assigns a globally monotonic msg_id (Snowflake-style) at write time. Clients sort by this ID, not by client timestamp.
  • Per-conversation ordering only: We only need ordering within a conversation — not globally. This is a key simplification that makes Cassandra partitioning work.
  • Clock skew on clients: Never trust client timestamps for ordering. Always use server-assigned seq IDs. Client timestamps go into created_at for display only.
// Snowflake ID structure for message ordering // 64 bits: [41 bits timestamp ms] [10 bits server_id] [13 bits seq] // Guarantees: monotonically increasing, sortable, no coordination needed msg_id = (timestamp_ms << 23) | (server_id << 13) | seq_per_ms
👥 Deep Dive 2: Group Messaging — The Fan-Out Problem
Fan-out on Write WhatsApp / Messenger
  • When a group message arrives, immediately copy it to every member's queue/inbox
  • Fast reads — each user's inbox always ready
  • Expensive writes: 1 message × 500 members = 500 writes
  • Best for groups up to ~500 members
Fan-out on Read Discord 100K channels
  • Store message once in channel/group. On read, fetch group's messages.
  • Cheap writes — single write regardless of group size
  • Expensive reads — every member reads from same location
  • Great for large groups, bad for per-user inbox features
💡 "I'd use fan-out on write for groups up to 500 members (WhatsApp limit). Beyond that, switch to fan-out on read (Discord model). The hybrid approach stores the message once and uses a pointer/cursor per member rather than full copy."
🟢 Deep Dive 3: Presence Service
  • Heartbeat: Client sends heartbeat every 5 seconds over WebSocket. Chat server updates Redis: SET presence:{user_id} {timestamp} EX 10
  • Last seen: When key expires → user is offline. last_seen = timestamp of final heartbeat.
  • The fan-out problem: User A has 500 friends. When A goes online, notify all 500. At scale this is 500M presence updates/sec. Must be throttled.
  • Subscription model: Only notify friends who are currently online. Pub/sub via Redis — friends subscribe to each other's presence channel.
  • Privacy: "Last seen" can be disabled. Show "online" only to contacts.
⚠️ "Presence is the sneaky scalability problem. 100M DAU × 1 heartbeat/5s = 20M writes/sec just for presence. Redis cluster with presence data sharded by user_id is essential."

🏆 What Separates Good from Great Answers
  • Explain WHY WebSockets by eliminating polling, long-polling, SSE first
  • Online vs offline path as two separate flows — most candidates only draw the happy path
  • Delivery receipt mechanics — the three-tick system requires ACK messages flowing in reverse from recipient to sender
  • Never trust client timestamps for ordering — proactively mention Snowflake server-side seq IDs

  • Media separation — upload direct to S3, message just carries the URL; chat servers never touch media bytes
  • Idempotency keys for deduplication — network retries will happen, clients must include a client-generated UUID
🔴 Common mistakes: (1) Using HTTP/REST for real-time delivery. (2) Storing media in the message DB. (3) Forgetting offline users entirely. (4) Using a single database for messages. (5) Fan-out on write for 100K member groups.

🛡️ Resilience Patterns
  • Circuit Breaker: After N failures to an upstream, open the circuit → fail fast for T seconds → half-open probe
  • Retry with backoff: Retry idempotent requests (GET) with exponential backoff + jitter. Never retry non-idempotent (POST) blindly.
  • Timeout enforcement: Gateway sets hard deadline per upstream. Prevents slow services from holding connections.
  • Bulkhead: Separate thread pools per upstream — one slow service can't exhaust gateway connections for all others
📡 Observability Built-in
  • Request ID injection: Gateway stamps every request with a UUID for distributed tracing (X-Request-ID header)
  • Latency histograms: p50/p99/p999 per route, per upstream — exported to Prometheus/Datadog
  • Error rate tracking: 4xx vs 5xx per service — feeds circuit breaker decisions
  • Access logs: Structured logs (timestamp, route, latency, status, client_id) → shipped to Kibana/Splunk
💡 Key point: "The gateway nodes are completely stateless — all shared state lives in Redis. This means I can scale gateway instances horizontally without any coordination. The only stateful component is the Redis cluster for rate limit counters."
⏱️ Rate Limiter — The Distributed Problem Hardest part

A single-node rate limiter is trivial. The interview is really asking: how do you enforce a consistent rate limit when there are 50 gateway nodes all serving the same client?

Option 1: Pure Redis
  • Single source of truth
  • Accurate across all nodes
  • Adds ~1–5ms latency per request
  • Redis becomes bottleneck at extreme scale
Option 2: Local Counter
  • Zero network overhead
  • Sub-millisecond decision
  • Inconsistent across nodes — client can 10× the limit if 10 nodes each allow full quota
  • Only works with sticky sessions
Option 3: Hybrid ✓ Best
  • Local counter handles 80% of traffic fast
  • Sync with Redis every 100ms or every N requests
  • Slight over-admission possible (acceptable)
  • Redis fails → fall back to local (fail-open)
💡 Recommended answer: "I'd use a hybrid approach — each gateway node maintains a local token bucket, syncing with Redis every 100ms. This gives sub-millisecond decisions on the hot path with ~10% over-admission tolerance."
🔑 Redis Implementation — Atomic Lua Script
-- Sliding Window Counter in Redis (atomic Lua — no race conditions) local key = KEYS[1] local limit = tonumber(ARGV[1]) local window = tonumber(ARGV[2]) local now = tonumber(ARGV[3]) redis.call('ZREMRANGEBYSCORE', key, 0, now - window * 1000) local count = redis.call('ZCARD', key) if count < limit then redis.call('ZADD', key, now, now) redis.call('EXPIRE', key, window) return 1 -- ALLOW else return 0 -- DENY → 429 end
⚠️ Why Lua? The check-then-increment must be atomic. Without it, two concurrent requests can both read count=99, both pass, and both increment to 100 — a race condition.
📋 Response Headers — Must Mention
# Always return these — clients can self-throttle X-RateLimit-Limit: 100 X-RateLimit-Remaining: 43 X-RateLimit-Reset: 1699001234 Retry-After: 47
💡 Mentioning these headers shows product thinking — well-behaved clients read these and back off automatically, reducing retry storms.

🔍 Deep Dive 1: URL Deduplication — Bloom Filter Most asked!

With 1 billion URLs, storing every seen URL in a hash set requires ~200 GB of RAM. A Bloom filter represents the same set with ~8–10 GB using probabilistic hashing — with a tunable false positive rate.

  • How it works: Hash each URL with k independent hash functions → set k bits in a bitarray. To check: if all k bits set → "probably seen". If any bit unset → "definitely new".
  • False positives: Bloom filter may say "seen" for a URL it hasn't crawled. Acceptable — we occasionally skip a valid URL.
  • No false negatives: If Bloom says "new", it's definitely new.
  • Size: For 1B URLs with 1% false positive rate → ~1.14 GB bitarray. Fits in Redis.
// Bloom filter check before crawl BloomFilter<String> filter = BloomFilter.create( Funnels.stringFunnel(UTF_8), 1_000_000_000L, // expected insertions 0.001 // 0.1% false positive rate ); boolean mightBeSeen(String url) { return filter.mightContain(normalize(url)); }
⚠️ Two-level dedup: Bloom filter for URL dedup (have we crawled this URL?) + content hash (SHA-256) for content dedup (is this page a duplicate of another?). Both are needed.
⚡ Deep Dive 2: URL Frontier — Priority + Politeness
Priority Queue
  • Score each URL: priority = f(PageRank, freshness_signal, inlink_count)
  • Use a Redis sorted set (ZADD with score) — O(log N) insert and pop
  • Multiple priority tiers: P0 (breaking news) → P3 (deep pagination)
Politeness Queue
  • Separate per-domain FIFO queue. Fetcher picks next URL only if now - last_fetch_time[domain] >= crawl_delay
  • Crawl delay sourced from robots.txt Crawl-delay directive, else default 1s
  • If domain is cooling down → skip to next domain's queue. Never block the whole worker.
📅 Deep Dive 3: Recrawl Scheduling
  • Change rate estimation: On each recrawl, compare content hash to previous. Track change frequency per URL over time → exponential moving average.
  • Adaptive scheduling: Frequently-changing page (news) → crawl every 15 minutes. Stable page (about-us) → crawl monthly.
  • Last-Modified + ETag: Send If-Modified-Since on recrawl. Server returns 304 Not Modified → skip re-storing, just update crawl timestamp.
  • Sitemap.xml signal: News sitemaps announce new content instantly — subscribe rather than poll.
// Adaptive recrawl interval formula double nextCrawlDelay(URL url) { double changeRate = history.getChangeRate(url); // changes/day EMA if (changeRate > 10) return 15; // minutes — breaking news if (changeRate > 1) return 360; // minutes — active blog if (changeRate == 0) return 43200;// minutes — 30 days (static) return 10080; // weekly default }

⚡ Kafka — The Backbone Deep dive this
Partitioning Strategy
  • Key = user_id: All events for one user go to same partition → ordering guaranteed per user. Used for fraud detection.
  • Key = listing_id: All events for one listing on same partition. Used for inventory, pricing signals.
  • Key = null (round-robin): Max throughput, no ordering guarantee. Used for metrics/logs.
  • Partition count: Rule of thumb — target 1–10 MB/s per partition. 50K/sec × 1KB = 50MB/s → 10–50 partitions per topic.
Producer Reliability
  • acks=all (acks=-1): Leader waits for all in-sync replicas to ACK. Zero data loss. Use for payment/booking events.
  • acks=1: Leader ACKs immediately. Risk of loss if leader crashes before replication. Use for metrics.
  • Idempotent producer: enable.idempotence=true — Kafka deduplicates retries using sequence numbers.
  • Local buffer + retry: SDK buffers events locally (disk-backed) if Kafka is unreachable.
🌊 Flink — Stateful Stream Processing
Windowing
  • Tumbling window: Non-overlapping fixed windows (e.g. count bookings every 1 min).
  • Sliding window: Overlapping windows (e.g. bookings in last 5 min, updated every 1 min).
  • Session window: Grouped by activity gap (e.g. user session ends after 30 min inactivity).
Late Data Handling
  • Event time vs processing time: Always use event time. A mobile event from an offline device may arrive hours late.
  • Watermarks: Flink advances a watermark = max_seen_event_time - allowed_lateness.
  • Allowed lateness: Window stays open for X extra seconds after watermark. Late events update and re-emit.
  • Side output: Events too late → DLQ or corrective batch.
// Flink: count bookings per listing per 5-min window with 30s late tolerance stream .keyBy(BookingEvent::getListingId) .window(TumblingEventTimeWindows.of(Time.minutes(5))) .allowedLateness(Time.seconds(30)) .sideOutputLateData(lateOutputTag) .aggregate(new BookingCountAggregator()) .addSink(redisSink);
⚠️ Exactly-once adds ~10–20% latency overhead due to checkpointing and transaction coordination. For non-critical streams (metrics, logs), at-least-once + idempotent sink is a fine trade-off.
🗄️ Storage Layer — S3 + Parquet + Delta Lake
Why Parquet?
  • Columnar format: Analytical queries read only the columns they need. "SELECT count(*) WHERE event_type='booking'" reads 1 column, not entire rows.
  • Predicate pushdown: Min/max stats per row group let Spark skip irrelevant pages entirely.
  • Compression: Snappy or Zstd on columnar data → 5–10× size reduction vs JSON.
  • Schema embedded: Self-describing — no separate schema lookup for old files.
Partitioning Strategy
  • Time-based partitioning: s3://events/event_type=booking/year=2024/month=11/day=15/hour=14/
  • Partition pruning: Queries like "show bookings yesterday" skip 364/365 partitions.
  • Small file problem: 5-min micro-batches create tiny files. Hourly compaction job merges to 128MB–1GB target.
  • Delta Lake: Adds ACID transactions on S3. Enables upserts, deletes (GDPR), schema evolution, and time travel queries.
🔄 Schema Evolution — Critical for Long-Running Pipelines
  • Schema Registry (Confluent): Every event schema is versioned. Producers register schema; consumers fetch by ID.
  • Backward compatibility: New schema can read old data. Add fields with defaults — never remove or rename fields.
  • Forward compatibility: Old schema can read new data. Consumers ignore unknown fields.
  • Full compatibility: Both directions. Most restrictive — only add optional fields. What Airbnb enforces on critical topics.
// Avro schema with evolution-safe design { "type": "record", "name": "BookingEvent", "fields": [ {"name": "event_id", "type": "string"}, {"name": "user_id", "type": "long"}, {"name": "event_time", "type": "long"}, // epoch ms — event time! // v2 addition — backward compatible (has default) {"name": "listing_country", "type": "string", "default": "US"} ] }

🔥 Failure Scenarios — Bring These Up
  • Consumer lag spike: Flink job slows down → lag builds in Kafka. Monitor with Burrow. Scale Flink parallelism. Kafka retains 7 days → no data loss.

⚡ CAP Theorem — State This First Always ask!
Consistency (C)
Every read receives the most recent write or an error. All nodes see the same data simultaneously.
Availability (A)
Every request gets a response (no error), even if data isn't the latest. System never goes down.
Partition Tolerance (P)
System continues operating even if network messages between nodes are lost. Always required in practice.
💡 P is non-negotiable in distributed systems. So the real choice is CP vs AP. For a general-purpose KV store: choose AP + tunable consistency. For coordination/config: choose CP (etcd).

🔵 Deep Dive 1: Consistent Hashing Most asked!
  • Naive hashing (key % N): Remap ALL keys when N changes. Catastrophic at scale.
  • Consistent hashing: Map keys AND nodes onto a circular ring (0 to 2³²). A key is owned by the first node clockwise from its hash position.
  • Virtual nodes (vnodes): Each physical node gets multiple positions on the ring (e.g. 100–150 vnodes). Fixes uneven distribution. When a node is added/removed, only ~1/N of total data moves.
  • Replication: Write to the primary node + next N-1 clockwise nodes on the ring.
// Consistent Hash Ring — Java sketch TreeMap<Integer, String> ring = new TreeMap<>(); void addNode(String nodeId) { for (int i = 0; i < 150; i++) { int hash = hash(nodeId + "-vnode-" + i); ring.put(hash, nodeId); } } String getNode(String key) { int hash = hash(key); Map.Entry<Integer, String> entry = ring.ceilingEntry(hash); return (entry != null) ? entry.getValue() : ring.firstEntry().getValue(); }
💡 "With virtual nodes, adding a node to a 100-node cluster causes ~1% of keys to migrate on average, instead of 100% with naive hashing."

⚠️ Sloppy Quorum (Hinted Handoff): If a replica node is down, write to a healthy neighbour with a hint. When the downed node recovers, hints are replayed. This improves write availability but means W+R > N doesn't guarantee strong consistency during partitions.
💾 Deep Dive 3: Storage Engine (LSM Tree)
  • MemTable: Writes land here first (sorted in-memory red-black tree). Fast O(log n) insert.
  • WAL (Write-Ahead Log): Every write logged to disk before MemTable. Crash recovery.
  • SSTable flush: When MemTable hits threshold (~64MB), flush to sorted immutable SSTable on disk.
  • Bloom Filter: Per-SSTable probabilistic filter. Avoids disk reads for non-existent keys.
  • Compaction: Background merge of SSTables to reclaim space and maintain read performance.
  • Tombstones: Deletes write a tombstone marker — physical deletion happens at compaction time.
// Write path in LSM-tree storage engine PUT(key, value): 1. Append (key, value, timestamp) → WAL // disk, sequential write — fast 2. Insert into MemTable (sorted skip list) // in-memory 3. If MemTable > 64MB → flush to SSTable on disk 4. Background: compact SSTables → merge + dedupe

🔴 Common mistakes: (1) Jumping to architecture before CAP decision. (2) Saying "just add more nodes" without explaining rebalancing. (3) Forgetting WAL — without it, a crash loses the MemTable. (4) Not mentioning tombstones for deletes.

✅ Functional Requirements
  • Produce messages — publishers write to a named topic
  • Consume messages — subscribers read from a topic, track their own offset
  • Topics + Partitions — topic splits into ordered partitions for parallelism
  • Consumer Groups — multiple independent consumers per topic, each gets all messages
  • Message retention — retain messages for configurable period (e.g. 7 days) regardless of consumption
  • Replay — consumer can seek to any past offset and reprocess
  • Ordering — guaranteed within a partition (not globally)
⚙️ Non-Functional Requirements
  • High throughput — millions of messages/sec (write-optimised)
  • Low latency — end-to-end < 10ms p99 for fire-and-forget producers
  • Durability — messages survive broker crashes (replication factor ≥ 3)
  • Scalability — add brokers/partitions with no downtime
  • Fault tolerance — no single point of failure; auto-leader election
  • Backpressure — slow consumers don't affect producers

✍️ Producer Write Path
1
Producer fetches cluster metadata (broker list, partition leaders) from any broker on startup — cached locally
2

3

4

5

👁️ Consumer Read Path
1
Consumer joins a group → Group Coordinator assigns partitions via Rebalance Protocol
2
Consumer polls partition leader: fetch(partition=0, offset=1234, maxBytes=1MB)
3
Broker returns batch of messages from that offset. Consumer processes them.
4
Consumer commits offset to __consumer_offsets topic — either auto (every 5s) or manual post-processing
5
On failure: consumer restarts, reads last committed offset → reprocesses from there (at-least-once)
💾 Deep Dive 1: Storage — The Append-Only Log Core insight

Each partition is an append-only, immutable log on disk. This is the key design insight that gives Kafka its throughput — sequential writes are 100× faster than random writes, and the OS page cache handles most reads without touching disk.

Segment 0 (old) msg 0 msg 1 … msg 999K → rolled to S3 after 24h
Segment 1 1.0M 1.1M … 1.9M ← Consumer A offset
Active Segment 2.0M 2.1M 2.2M appending… ← Producer writes here
  • Segment files: Log split into 1GB files. Closed segments are immutable. Only the active segment receives writes.
  • Index files: Each segment has a sparse offset→position index. Binary search to find message by offset in O(log n).
  • Zero-copy reads: sendfile() syscall transfers data from page cache directly to network socket — bypasses user space. Critical for high-throughput consumers.
  • Log compaction: Alternative to time-based retention. Keep only the latest value per key. Used for event sourcing / CDC use cases.
  • Page cache exploitation: Kafka relies on Linux OS page cache. Sequential reads are almost always served from RAM.
// Partition log on disk — files per partition /var/kafka/data/orders-0/ 00000000000000000000.log // segment 0 — messages offset 0 to 999K 00000000000000000000.index 00000000000001000000.log // segment 1 — active segment 00000000000001000000.index leader-epoch-checkpoint
🔁 Deep Dive 2: Replication — ISR (In-Sync Replicas)
  • ISR set: The set of replicas that are "caught up" to the leader (within replica.lag.time.max.ms, default 10s).
  • High-watermark (HW): The highest offset that all ISR replicas have confirmed. Consumers can only read up to HW.
  • acks=all: Producer waits for all ISR replicas to acknowledge before getting success response. Most durable setting.
  • Leader failure: ZooKeeper/KRaft detects failure → elects new leader from ISR → producers/consumers transparently reroute.
  • Unclean leader election: If ISR is empty, allow stale replica to become leader? Trades durability for availability. Off by default.
⚠️ Key interview point: "If min.insync.replicas=2 and replication.factor=3, the cluster tolerates 1 broker failure with no data loss. If 2 brokers fail simultaneously, producers with acks=all will block/error — it chooses durability over availability."
👥 Deep Dive 3: Consumer Groups + Rebalancing
  • Group Coordinator: One broker elected as coordinator for each consumer group. Manages membership, heartbeats, offset commits.
  • Partition assignment: Each partition assigned to exactly one consumer in the group. Max parallelism = partition count.
  • Heartbeat: Consumer sends heartbeat every session.timeout.ms (default 10s). No heartbeat → coordinator triggers rebalance.
  • Cooperative rebalance (v2.4+): Only revoke partitions that need to move. No stop-the-world pause.
// Consumer group assignment Topic "orders" — 3 partitions Group A (3 consumers): Consumer A1 → Partition 0 Consumer A2 → Partition 1 Consumer A3 → Partition 2 Group A (4 consumers): A1→P0, A2→P1, A3→P2, A4→idle // A4 gets nothing — can't exceed partition count!

🎯 Exactly-Once — How It Actually Works
Idempotent Producer
  • Broker assigns producer a PID (Producer ID) and tracks a sequence number per partition
  • If producer retries and broker already has that sequence number → deduplicate silently
  • Enabled with: enable.idempotence=true
Kafka Transactions
  • Atomic write across multiple partitions + offset commit in one transaction
  • Transaction coordinator broker manages 2-phase commit
  • Consumer sets isolation.level=read_committed → only sees committed data
  • Use for: consume → transform → produce pipelines where all three must be atomic
// Kafka exactly-once: consume-transform-produce pattern producer.initTransactions(); try { producer.beginTransaction(); ConsumerRecords records = consumer.poll(Duration.ofMs(100)); for (record : records) { producer.send(transform(record)); } producer.sendOffsetsToTransaction(offsets, groupId); producer.commitTransaction(); } catch (Exception e) { producer.abortTransaction(); }
💀 Dead Letter Queue (DLQ) Pattern
  • Problem: A malformed or unprocessable message ("poison pill") blocks a consumer partition forever on retry
  • Solution: After N retries, route the message to a separate orders-dlq topic instead of retrying infinitely
  • DLQ contains: Original message + metadata (original topic, partition, offset, error reason, timestamp)
  • Operations: Engineers inspect DLQ, fix the bug, then replay fixed messages back to the original topic
⚠️ "A poison pill without a DLQ will halt an entire partition indefinitely — the consumer keeps retrying offset 1234 forever, and all messages at offset 1235, 1236… pile up unprocessed. Always implement a DLQ or circuit-breaker retry policy."

🏆 What Separates Good from Great Answers
  • Explain WHY append-only log: Sequential disk writes saturate disk bandwidth (500 MB/s vs 50 MB/s random). This is the fundamental reason Kafka outperforms traditional queues — not clever code, just physics.
  • High-watermark and consumer read isolation: Consumers can't read past HW — prevents reading uncommitted data. Most candidates miss this.
  • Pull vs Push — and why pull wins at scale: Push requires broker to track consumer speed. Pull lets consumers read at their own pace, naturally handles backpressure.
  • Partition count = max consumer parallelism: If you have 10 consumers in a group but only 3 partitions, 7 consumers are idle.
  • Log compaction for CDC: Shows you know the difference between stream retention and compacted topics — demonstrates production experience.
  • Tiered storage: After messages are 24h old, almost no consumer reads them. Offload to S3 at 1/10th the cost.
  • KRaft mode: Kafka is eliminating ZooKeeper dependency (fully removed in Kafka 4.0) — signals you follow the ecosystem actively.
🔴 Common mistakes: (1) Saying "global ordering" without noting it requires 1 partition and kills throughput. (2) Not explaining consumer group rebalancing. (3) Conflating RabbitMQ (delete after ACK) with Kafka (retain regardless). (4) Forgetting the DLQ / poison pill problem. (5) Saying "just add more consumers" without mentioning they can't exceed partition count.
